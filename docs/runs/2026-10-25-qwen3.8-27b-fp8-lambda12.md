# 2026-10-25 — Qwen3.8-27B-FP8 on 2x V100-SXM2

Status: **validated for correctness; performance limited by the dense decode
path, not by the FP8 weight format.**

This is the first recorded FP8 run of the layer. It answers one question: does
the official block-FP8 checkpoint load and serve on SM70 through the TurboMind
W8A16 dense kernels? It does. It does not yet answer how fast the path can go.

## Throughput

Cold prefix per request (per-request salt, so the prefix cache cannot turn a
"cold" prefill into a hit). 128 output tokens, 1 warmup + 2 reps per context.

| Context | TTFT (s) | Prefill tok/s | Decode tok/s |
|---|---|---|---|
| 1K | 0.60 | 1666–1674 | 10.31–10.34 |
| 8K | 4.07 | 1972 | 10.29–10.34 |
| 28K | 16.0 | 1749–1755 | 10.43–10.44 |

Decode is flat across context length, which means it is not KV-bandwidth bound.

## What this run establishes

1. **FP8 dense works end to end on SM70.** Official checkpoint, no requant, no
   dequantization step, both TP ranks on the TurboMind kernel.
2. **FP8 did not move decode throughput.** The earlier W4A16 Marlin run on the
   same model measured 8.6 tok/s; FP8 measures 10.3. The weight format is not
   the bottleneck.
3. **The fast decode path is KV-dtype gated.** Every decode batch logs
   `SM70 CUDA decode partial disabled: kv_dtype(fp8=False,e5m2=False)`. The
   partial-decode kernel only engages for FP8/E5M2 KV, not for fp16 KV. This is
   a different cause from the disabled CUDA graph.
4. **CUDA graph is still off** because of the dense hybrid metadata bug
   (`forward_metadata=None` reaching `triton_backend.forward_decode`).

Together, (2)–(4) point the next perf work at the dense decode path (KV dtype,
graph capture, GDN decode), not at quantized GEMM.

## Non-blocking observations

- `post-warmup flush_cache failed` with a `400 Bad Request` traceback right
  before the server reports ready. The server serves normally afterwards.
- 28K was used instead of 32K to leave room for 128 output tokens under
  `--context-length 32768`.

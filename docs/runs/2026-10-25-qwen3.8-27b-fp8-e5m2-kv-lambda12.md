# 2026-10-25 — Qwen3.8-27B-FP8 with E5M2 KV on 2x V100-SXM2

Status: **E5M2 KV is not usable with the default fast decode kernel; without
that kernel it gives no throughput gain.**

This run tested the hypothesis behind #30: that the fast decode path is gated on
KV dtype, so switching from fp16 to `fp8_e5m2` would unlock it and lift decode.

The gate is real. The kernel behind it is wrong.

## Stack

Same as `2026-10-25-qwen3.8-27b-fp8-lambda12.md`: SGLang
`dg1kjd/sglang-sxm2` @ `73abfe1` + 3 local patches, `torch 2.9.1+cu128`,
`flashinfer 0.6.12`, image `cuda_12.8.0-devel-ubuntu24.04.sif`, lambda12,
2x V100-SXM2-32GB, TP2, context 32768.

Only two settings differ between the runs:

| Setting | Value |
|---|---|
| `--kv-cache-dtype` | `fp8_e5m2` |
| `SGLANG_V100_DECODE_CUDA` | unset (default on) or `0` |

## Correctness matrix

Greedy, `temperature=0`, `ignore_eos=true`, short prompts.

| CUDA partial | Request | Output |
|---|---|---|
| on | 1st after startup | `Paris. The capital of Germany is Berlin. ...` |
| on | 2nd, same prompt | ` Paris!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!` |
| on | 3rd, same prompt | `!!!!!!!!!!!!!!!!!!!!!!!!` |
| on | unique prefixes (`alpha ...`, `bravo ...`) | `!!!!` every time |
| off | same prompt twice | correct both times |
| off | `alpha The capital of Italy is` | ` Rome.` |
| off | `The capital of Germany is` | ` Berlin.` |

The first request after startup is correct; everything after it is corrupted.
Disabling `SGLANG_V100_DECODE_CUDA` restores stable output, which isolates the
fault to the hand-written partial rather than the e5m2 cache itself.

Log with the kernel enabled:

```
SM70 (V100): CUDA long-context decode partial loaded.
KV Cache is allocated. dtype: torch.float8_e5m2, #tokens: 392560
```

Log with it disabled:

```
SM70 CUDA decode partial disabled: cuda_unavailable(env=False,cap=(7, 0))
```

## Throughput (kernel disabled)

Cold prefix, 128 output tokens, 1 warmup + 2 reps. fp16 numbers are the earlier
run on the same host and stack.

| Context | KV | TTFT (s) | Prefill tok/s | Decode tok/s |
|---|---|---|---|---|
| 1K | fp16 | 0.60 | 1666-1674 | 10.31-10.34 |
| 1K | e5m2 | 0.61-0.63 | 1598-1661 | 9.36-9.88 |
| 8K | fp16 | 4.07 | 1972 | 10.29-10.34 |
| 8K | e5m2 | 4.06-4.07 | 1971-1974 | 9.63-10.48 |
| 28K | fp16 | 16.0 | 1749-1755 | 10.43-10.44 |
| 28K | e5m2 | 16.05-16.07 | 1750-1751 | 10.52-10.55 |

Within noise of the fp16 baseline. E5M2 doubles KV capacity (196,272 to 392,560
tokens) but does not move the decode rate while the partial is off.

## Findings

1. The KV-dtype gate is exactly as read from the source: the partial requires
   `fp8_kv and e5m2_kv`. fp16 KV always logs the disabled reason.
2. The partial kernel corrupts output with e5m2 KV, starting from the second
   request. First-request-correct then permanent corruption suggests state or
   page metadata is written on the first pass and misread afterwards; the
   trigger is not context length.
3. With the kernel disabled, e5m2 is performance-neutral and doubles capacity.
   The capacity may still matter for agentic workloads, but the advertised fast
   path is the reason to use e5m2, and that path is currently broken.
4. The disabled warning is emitted per layer per batch: 3,843 lines from a few
   short requests, which also makes any measurement in that configuration
   suspect.

## Next steps

- Fix or disable the partial until it is correct (#51).
- Make the disabled warning once-per-reason (#52).
- Re-run this matrix after the fix; the expected gain is at long context, where
  the split-KV partial matters.

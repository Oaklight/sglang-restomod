# 2026-10-26 — Qwen3.8-27B-FP8 on 2x V100: MTP and KV dtype by context length

Status: **MTP pays below ~12k and costs 33% at 32k; the KV dtype question is
decided by the decode partial, which is blocked by #51.**

Every number below comes from the same harness: one streaming `/generate`
request per context, unique random prefix, `temperature=0`, `ignore_eos`, 64
output tokens, CUDA graph on, TP2 on lambda12, ctx 32768. Stack is the fork
`dg1kjd/sglang-sxm2` @ `73abfe1` plus the lab patches, i.e. the same stack as
the other 2026-10-26 records.

## The matrix

Decode tok/s, graph on:

| KV dtype | MTP | 8k | 32k | output |
|---|---|---|---|---|
| fp16 | on | **45.7** | 20.5 | correct |
| fp16 | off | 34.4 | **30.4** | correct |
| e5m2 | off, TileLang partial | 33.8 | 30.0 | correct |
| e5m2 | off, CUDA partial | 34.7 | 33.5 | **corrupt** (#51) |

Accept length with MTP is 3.05 at 8k and 3.20 at 32k, so the MTP loss at long
context is not an acceptance problem — the verify step itself gets more
expensive than the tokens it saves.

## MTP by context

MTP is worth +33% at 8k and -33% at 32k, on identical fp16 KV and identical
harness. The crossover sits between 12.7k and 17.0k, so **switch MTP off above
~16k**. Both arms were measured on the same grid:

| Context | fp16, MTP | fp16, no MTP | MTP delta |
|---|---|---|---|
| 8.2k | 45.7 | 34.4 | +33% |
| 12.7k | 34.8 | 33.5 | +4% |
| 17.0k | 30.7 | 32.8 | -6% |
| 25.6k | 23.3 | 31.4 | -26% |
| 32.4k | 20.5 | 30.4 | -33% |

Mechanism: each MTP step runs one target forward over `1 + draft` positions, so
the attention and the weight read are paid once per *verify*, not once per
accepted token. At 8k the accepted 3.05 tokens per verify make that a 3x win.
As context grows the per-verify cost grows with KV length while the accept
length stays flat, so the win shrinks and inverts. Nothing about the draft head
changes; it is purely the verify step's cost curve.

## KV dtype

e5m2 changes nothing by itself. With the TileLang decode partial the two dtypes
are within 2% at both 8k (33.8 vs 34.4) and 32k (30.0 vs 30.4) — the halved KV
bytes do not show up in decode because the step is not KV-bandwidth-bound at
these lengths.

The hand-written CUDA partial is what changes the picture: **33.5 vs 30.0 at
32k, +11.7%**, and 34.7 vs 33.8 at 8k, +2.7%. So the partial — not the dtype —
is the entire value of the e5m2 path, which is the claim in #51.

It is also corrupt: greedy output degrades to `A paged KV cache!!!!!!!` after
the first request. Both arms above were run with the graph on, and the partial
loads and runs under capture (`Capture target decode CUDA graph begin`,
`decode 15.59 s`, two `CUDA long-context decode partial loaded` lines), so the
graph is not the obstacle. Until #51 is fixed the usable long-context config is
e5m2 with `SGLANG_V100_DECODE_CUDA=0`, which is not faster than fp16.

## Correction to the MTP record

`2026-10-26-qwen3.8-27b-mtp-lambda12.md` says the partial "did not load in this
run … every run where it did load had CUDA graph off, while this one had the
graph on." That attribution was wrong. The partial loads fine with the graph on;
what suppresses it is MTP. With `--speculative-algorithm NEXTN` the decode runs
in the target-verify path, which does not go through
`_paged_adapter.grouped_decode_forward`, so the gate is never reached (#73).
Graph on/off is irrelevant.

The consequence for that record's e5m2 table (32k decode 4.9 tok/s) is that the
number is e5m2 **with MTP and without the partial**, which is the worst of both:
MTP costs 33% at 32k, and without the partial e5m2 has no decode advantage to
offset it. Read as a general statement "e5m2 is a net loss" is wrong; read as
"e5m2 with MTP is a net loss", it is right.

## Serving profiles

| Workload | Config | Why |
|---|---|---|
| Interactive, context <= 12k | fp16 KV + graph + MTP | 45.7 tok/s at 8k, 34.8 at 12.7k |
| Long context, > 16k | fp16 KV + graph, **no MTP** | 32.8 at 17k, 30.4 at 32k; +48% over MTP at 32k |
| Long context, once #51 is fixed | e5m2 + graph, no MTP, partial on | 33.5 at 32k |

Prefill does not change the ranking within a config: with MTP off, fp16 and e5m2
both prefill 32k at ~1,730 tok/s (1,730 and 1,727), so the dtype buys nothing
there. With MTP on the two dtypes disagree badly (709 tok/s for fp16, 1,464 for
e5m2 in the earlier run) and both are far below the no-MTP figure. That gap is
not explained yet and is worth a separate look; it does not affect the decode
ranking above, where every row is measured with the same harness.
